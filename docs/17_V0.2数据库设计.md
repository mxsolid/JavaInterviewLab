# 17 V0.2 数据库设计

本文件记录 V0.2 学习闭环表结构。

## 表与职责

| 表 | 职责 |
|---|---|
| `profile` | V0.2 的本地学习档案。当前创建唯一默认档案，避免用户状态没有归属。 |
| `study_plan` | 一条系统学习路线，如 15 天推荐。 |
| `study_plan_day` | 路线中的 Day 1 至 Day N。 |
| `study_plan_item` | 某天关联的专题、题目；未来可关联场景。 |
| `profile_plan` | 学习档案选择过的路线，以及当前 active 路线。 |
| `question_attempt` | 一次练习的 append-only 历史事实。 |
| `study_progress` | 每题当前掌握度、错误次数和错题状态快照。 |
| `favorite` | 当前用户收藏偏好，可取消。 |
| `note` | 用户对题目或专题的当前笔记，使用 version 乐观锁。 |
| `review_task` | 下一次复习计划及已完成历史。 |

`profile_plan` 的部分唯一索引 `uk_profile_plan_active` 保证一个 profile 同时只有一条 active 路线。切换路线时旧记录改为 inactive，而不是删除。

## 计划项关系

`study_plan_item` 使用 `target_type + target_id`：

- `TOPIC` 指向 `topic.id`。
- `QUESTION` 指向 `question.id`。
- `SCENARIO` 为 V0.3 预留。

这是一个受控的多目标关系。单列 `target_id` 无法同时建立多个外键，因此系统初始化只从受控 JSON 中解析已存在的专题和题目；普通 API 不提供计划项随意写入入口。

## 索引

| 索引 | 支持的查询 |
|---|---|
| `idx_study_plan_day_plan_day` | 查询一条路线的逐日计划、查询 Day N。 |
| `idx_study_plan_item_day_sort` | 查询某天的关联内容并保持固定顺序。 |
| `idx_profile_plan_active` | 读取默认用户的当前路线。 |

未为低频写入表添加额外索引，避免路线初始化和内容调整承担无用写入成本。

## B02 答题历史

`question_attempt` 使用 `(profile_id, client_attempt_id)` 唯一约束。前端一次练习生成 UUID，网络重试复用 UUID；数据库 `ON CONFLICT DO NOTHING` 是并发下的最终幂等防线。

按 `(profile_id, question_id, created_at DESC)` 建索引，用于读取某题最近练习历史。该表不提供普通 update/delete。

## B03-B06 学习状态

`study_progress` 以 `(profile_id, question_id)` 唯一，保存当前 `stage`、`mastery_level`、答题次数、错误次数、错题激活状态和最后学习时间。提交时先锁定 profile 行，覆盖首次 progress 尚不存在时无法行锁的并发窗口。

`favorite` 使用 `(profile_id, target_type, target_id)` 唯一约束。`note` 使用相同目标唯一约束和 `version`，更新 SQL 必须同时匹配 version。`review_task` 的部分唯一索引 `uk_review_task_pending` 限制同一用户同一题只有一条 `PENDING` 任务；查询今日任务由 `idx_review_task_profile_pending_due` 支持。
